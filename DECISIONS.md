# Technical decisions

This file explains the important choices behind Ember & Oak Coffee Roasters, in plain language. Each entry says
**what** was decided, **why**, and what we gave up (the **trade-off**). Where it helps, there's a short
**"How to explain it in an interview"** line.

It grows with the project: every phase adds its own section.

---

## Phase 1 — The store

### 1. Next.js with the App Router

**What.** The site is built with Next.js 16 using the App Router (the `src/app` folder), React 19 and TypeScript.

**Why.** Next.js gives us server rendering (good for SEO and fast first loads), API endpoints in the same project,
image optimization and a one-click deploy on Vercel. The App Router lets pages be **Server Components** by default:
they run on the server, can talk to the database directly, and send plain HTML to the browser. Only the interactive
parts (cart buttons, filters) are **Client Components** marked with `"use client"`.

**Trade-off.** The App Router has more concepts to learn (server vs. client components, caching rules) than a
classic single-page React app.

> **Interview:** "Pages render on the server and read the database directly, so there's no extra API layer for
> reads. Only interactive widgets ship JavaScript to the browser."

### 2. TypeScript everywhere

**What.** All code is TypeScript, including the database client (generated by Prisma) and the seed script.

**Why.** Types catch mistakes before the code runs — for example, passing a price in dollars where cents are
expected, or misspelling a roast level. The editor also autocompletes database fields.

### 3. PostgreSQL + Prisma 7

**What.** Products live in PostgreSQL. We talk to it through Prisma, an ORM that generates a typed client from
`prisma/schema.prisma`. Prisma 7 uses a "driver adapter" (`@prisma/adapter-pg`) that runs on the standard `pg`
Node.js driver.

**Why.**
- Postgres is reliable, free on Neon/Vercel, and supports array columns (we store tasting notes and brew methods as
  arrays, which makes "brew method is espresso OR filter" a one-line query).
- Prisma migrations (`prisma/migrations/`) give us a versioned history of the database structure, just like git
  does for code.
- Enums (`RoastLevel`, `BrewMethod`) mean the database itself rejects invalid values.

**Version note.** At the time of writing, npm's `latest` tag for the `prisma` CLI pointed to an 8.0 *release
candidate*, while the client was 7.10.0. We pinned both to exactly `7.10.0` so the CLI and client always match and
we don't ship pre-release software.

**Security note.** `npm audit` flagged two high-severity issues in packages the Prisma CLI pulls in (`deepmerge-ts`,
`mysql2`). Neither is used at runtime by our app, but instead of ignoring them we added `overrides` in
`package.json` to force the patched versions. `npm audit` now reports 0 vulnerabilities.

### 4. Money is stored as integer cents

**What.** `$19.50` is stored as `1950`. Formatting to dollars happens only when displaying (`src/lib/money.ts`).

**Why.** Computers can't represent most decimal fractions exactly: in JavaScript `0.1 + 0.2` is
`0.30000000000000004`. With integers, `1950 × 3 = 5850` is always exact. Stripe also works in cents, so no
conversion is needed at checkout.

> **Interview:** "Never use floating point for money. I store cents as integers and only format at the edge."

### 5. Prices are always calculated on the server

**What.** The browser's cart only stores *which* products and *how many* (plus the grind). To show totals, the cart
page sends that list to `POST /api/cart/quote`, which loads current prices and stock from the database and runs
`priceCart()` in `src/lib/pricing.ts`.

**Why.** Anything in the browser can be edited by the user (developer tools, localStorage). If the browser sent
prices, a customer could change `$64` to `$0.01`. Here, a tampered price is simply ignored — there's a unit test and
an E2E check proving it. The same function will price the Stripe checkout in Phase 2, so the number the customer sees
is the number they pay.

`priceCart()` also:
- clamps quantities to stock and to 10 per line,
- merges duplicate lines (same coffee, same grind),
- drops the grind option for accessories (you can't grind a grinder),
- applies the shipping rule ($6 flat, free from $50).

It's a *pure function* (same input → same output, no database access), so it's easy to test thoroughly.

**Trade-off.** The cart page makes one small request every time the cart changes. That's cheap and worth it.

### 6. The cart lives in localStorage

**What.** The cart is kept in the browser's `localStorage` (`src/lib/cart/store.ts`) and read through React's
`useSyncExternalStore`.

**Why.**
- No login is needed to shop, and the cart survives page reloads and browser restarts.
- `useSyncExternalStore` is React's official way to read outside data. It avoids a common bug called a *hydration
  mismatch*: the server can't see localStorage, so it renders an empty cart; React then swaps in the saved cart
  right after the page loads, without errors.
- It also listens to the `storage` event, so two open tabs stay in sync.
- Data read from storage is validated with Zod. If it's corrupted or from an older version, we start with an empty
  cart instead of crashing.

**Trade-off.** The cart doesn't follow the customer across devices. For a small store without accounts, that's the
normal behavior.

### 7. Catalog filters live in the URL

**What.** Filtering by roast, brew method, category and price changes the URL, e.g.
`/shop?roast=LIGHT&brew=FILTER&maxPrice=25`. The server reads the URL and queries the database.

**Why.** Filtered pages can be bookmarked and shared, the back button works, and the chatbot (Phase 3) can link to
a filtered view.

Because anyone can type anything into a URL, `parseCatalogFilters()` uses a Zod schema that **never throws**: unknown
values are dropped, a reversed price range is swapped. Bad input gives sensible results instead of an error page.

**Optimistic UI.** Changing a filter needs a server round trip. Without extra work, a checkbox would only look
checked after the new results arrived, which feels broken on a slow connection. The Playwright test caught this.
We use React's `useOptimistic` so the control updates instantly while results load.

### 8. Pages that show products render on every request

**What.** The home, shop and product pages use `export const dynamic = "force-dynamic"`.

**Why.** They show live stock ("Only 6 left") and prices. Static pages built at deploy time would show stale stock
until the next deploy. The catalog is small, so a database query per page view is fast and cheap.

**Trade-off.** Slightly more database load than static pages. If traffic grew, we could cache pages for a minute
(Incremental Static Regeneration) and refresh them when stock changes.

### 9. Images: downloaded from Unsplash, optimized, served locally

**What.** Product and site photos come from Unsplash (free license). We downloaded them, resized them to WebP (all
under 250 KB) and put them in `public/images/`. Pages use `next/image`, which serves the right size for each screen.
Photographers are credited in the footer and the README (`src/data/photo-credits.ts`).

**Why.** Serving images ourselves means the store never breaks if a third-party URL changes, and we control file
sizes. Each photographer credit was verified against Unsplash's own download filename.

We deliberately skipped photos showing real coffee brands' packaging, because the brand must be 100% original.

### 10. One file for policies and FAQ

**What.** Shipping, returns, payment rules and FAQ answers live in `src/content/store-info.ts`. The FAQ page renders
it. In Phase 3, the chatbot will be given the same text.

**Why.** A single source of truth means the website and the bot can never contradict each other. The shipping price
in the policy text is even computed from the same constant that the pricing code uses.

### 11. The seed catalog is a TypeScript file

**What.** The 12 products are defined in `src/data/catalog.ts`. `npm run db:seed` loads them with `upsert` (insert
or update by slug).

**Why.** Running the seed twice doesn't create duplicates — it resets prices and stock to the seed values. Phase 6's
demo cleanup job will reuse this file to restore stock.

### 12. Design system: Tailwind CSS 4 + shadcn/ui

**What.** Styling uses Tailwind CSS utility classes. Base components (buttons, sheet, accordion…) come from
shadcn/ui, which *copies* the component code into `src/components/ui/` instead of installing a closed library.

**Why.** We own the component code, so we could restyle it to the brand: bigger touch targets, a stronger focus
ring, accessible slider thumbs. Brand colors are CSS variables in `src/app/globals.css`.

### 13. Accessibility

What we did, and why each matters:

- **Contrast.** Every text color was checked numerically against WCAG AA (4.5:1). The lowest pair, ember-orange
  text on cream, is 5.04:1.
- **Keyboard.** A visible focus ring on every interactive element, and a "Skip to content" link.
- **Labels.** Every form field has a real `<label>`. Filters use native checkboxes; the price slider thumbs are
  named "Minimum/Maximum price". Icon-only buttons have `aria-label`s.
- **Specific button names.** Product grids used to have many buttons all called "Add to cart". Screen-reader users
  who jump between buttons couldn't tell them apart, so each is now named "Add Huila Hearth to cart".
- **Alt text** on meaningful images; decorative images use `alt=""` so screen readers skip them.
- **Touch targets** of at least 40px, and no horizontal scrolling on phones (checked automatically).
- **Reduced motion** is respected.

### 14. Local development setup

- **Docker Compose** runs Postgres on port **5433** (5432 was taken by another project) with a second database,
  `ember_oak_test`, so tests never touch development data.
- The dev server runs on port **3100** for the same reason.
- **OneDrive note.** The project folder is inside OneDrive, which locks files while syncing. That broke
  `create-next-app` (EPERM errors), so the app was scaffolded in a temp folder and copied in. Excluding
  `node_modules` and `.next` from OneDrive sync is recommended.
- **npm install scripts.** npm 11 blocks packages' install scripts until approved. We approved only four known
  ones (Prisma, Prisma engines, esbuild, unrs-resolver); they're listed under `allowScripts` in `package.json`.

### 15. Testing setup

- **Vitest** for unit and component tests, **React Testing Library** for rendering components, **Playwright**
  for end-to-end tests in a real browser on both a desktop and a mobile viewport.
- We don't use `@vitejs/plugin-react`: Vite 8 compiles JSX natively, and that plugin's dependencies conflicted with
  shadcn's. One less dependency.
- `server-only` is replaced by an empty module in tests (it deliberately throws outside the Next.js server).

### 16. Git workflow

- One branch per phase (`feat/store`, `feat/checkout`, …), merged into `main` when the phase is approved.
- Small commits following **Conventional Commits** (`feat(cart): …`, `fix(a11y): …`, `test(e2e): …`), with a body
  explaining *why* when it isn't obvious. Every commit passes typecheck.
- Secrets never go in git: `.env.local` is ignored and `.env.example` documents every variable.
